# Подключение Astro Orbi к тому же MCP

Код первой версии: текстовые черновики, точное согласование, постоянная очередь,
публикация в фоне, чтение своих постов/ответов/статистики. Генерация текстов идёт
в чате с ассистентом; самостоятельная генерация AI по расписанию пока не включена.
Нет отправки тестовых постов при подключении. Все внешние записи выключены по умолчанию.

## 1. Доступ через Meta

1. В https://developers.facebook.com/apps/ создать приложение с use case Threads API.
2. Для собственного аккаунта настроить роль Threads Tester для `astro_orbi` и
   принять приглашение в настройках разрешений сайтов этого аккаунта Threads.
3. Выдать `threads_basic`, `threads_content_publish`, `threads_read_replies` и
   `threads_manage_replies` для публикаций и ответов. Для статистики добавить
   `threads_manage_insights`.
4. Получить **долгоживущий пользовательский Threads access token** через настройки
   приложения/официальный OAuth. Если получен короткий токен, сначала обменять его
   по инструкции Meta. Этот сервер не реализует страницу входа Meta/OAuth callback.
5. Сохранить токен напрямую в Render Environment как `THREADS_ACCESS_TOKEN`.
   Пароль аккаунта, токен и App Secret не отправлять в чат или GitHub.

Имена разделов Meta могут меняться. Для доступа пользователей без роли в приложении
действуют требования Meta к App Review и публикации приложения; здесь настраивается
собственный аккаунт. Только наличие роли и действительных разрешений API определит
доступ; ссылка на публичный профиль не является авторизацией.

Официальные источники:
- https://developers.facebook.com/docs/threads/get-started/
- https://developers.facebook.com/docs/threads/get-started/long-lived-tokens/
- https://www.postman.com/meta/threads/collection/dht3nzz/threads-api
- https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api

## 2. Render Environment

После объединения этой ветки с main и деплоя добавить:

| Переменная | Значение |
| --- | --- |
| `ENABLE_THREADS` | `true` |
| `THREADS_ACCESS_TOKEN` | Долгоживущий токен аккаунта `astro_orbi` |
| `THREADS_ENABLE_PUBLISHING` | Сначала `false` |
| `THREADS_REDIS_URL` | Необязательно: отдельный постоянный Redis. Без него используется `OAUTH_REDIS_URL` |

Записи Astro Orbi хранятся в отдельном пространстве ключей `astro-orbi:threads:v1:`.
Данные и обновлённый токен зашифрованы ключом, производным от существующего
`FASTMCP_SERVER_AUTH_OAUTH_PROXY_JWT_SIGNING_KEY`. Этот ключ должен оставаться постоянным.
Хранилище должно иметь persistence и `noeviction`; временный диск не используется.

Веб-сервис с фоновым процессом должен работать постоянно. Эта версия не создаёт
отдельный платный сервис. Новый процесс получает очередь из Redis. Развёртывание
и ротацию ключей следует проводить до постановки реальных постов в очередь.

## 3. Проверка подключения без публикации

Обновить список инструментов подключённого MCP в клиенте и вызвать `threads_status`.
Ожидается `connected=true`, `username` профиля проверяется как `astro_orbi`,
публикация остаётся выключенной. ID аккаунта сервер получает из API и закрепляет
в хранилище; ID не нужно угадывать или копировать из Instagram.
Далее проверить `threads_list_posts`; дополнительные права — чтением ответов
и статистики собственного поста. Не включать запись, пока профиль не совпадает.

Затем задать `THREADS_ENABLE_PUBLISHING=true`, выполнить деплой и снова проверить
`threads_status`. Это разрешает постановку **одобренных** черновиков в очередь;
само по себе не создаёт ни одного поста.

Для ответа на комментарий передать `post_id` и `reply_to_id` при создании
черновика. MCP проверит принадлежность комментария ветке своего поста. В
предпросмотре будет `reply_target`; согласование привязано к этому адресату,
тексту и времени. Для другого адресата создать отдельный черновик.

## 4. Работа с черновиками

1. `threads_project_brief`, затем `threads_list_posts`: прочитать правила и историю.
2. `threads_save_draft(text, publish_at)` с конкретным временем и часовым поясом,
   например ISO-8601 с `+05:00`. Интервал: от минуты до 90 дней в будущем.
3. `threads_preview_draft(draft_id)`: показать владельцу текст, аккаунт, дату, время.
4. Только по его одобрению вызвать `threads_approve_draft(draft_id, expected_revision)`.
5. `threads_list_drafts`: посмотреть `queued`, затем `published` и `post_id`.
6. `threads_cancel_draft` снимает черновик с очереди до начала отправки.

Изменение текста или времени переводит даже согласованную запись обратно в `draft`.
Одобрение привязано к revision, тексту, времени и ID аккаунта. Автоответов клиентам
и произвольных HTTP-запросов через MCP нет.

## Отказы и границы проверки

- Очередь проверяется примерно раз в минуту. Это не гарантия публикации в точную секунду.
- При отставании более часа статус `missed`: требуется новое время и согласование.
- Redis WATCH гарантирует, что одновременные процессы не заберут один черновик дважды.
- После таймаута, неоднозначной ошибки или перезапуска в ходе отправки статус
  `needs_review`; неизвестный результат не отправляется повторно автоматически.
  Проверить профиль перед созданием нового поста. Удаление или редактирование уже
  опубликованного поста здесь не реализовано.
- Долгоживущий токен обновляется раз в семь дней; новая версия остаётся зашифрованной
  в Redis. Отзыв разрешений или истечение токена потребует нового входа в Meta и
  нового значения `THREADS_ACCESS_TOKEN`. Статус и ошибки обновления видны в MCP.
- Проект STELLA сохраняет свой набор инструментов, авторизацию и настройки рассылок.
- Локальные тесты имитируют Threads/Redis. Живая авторизация, реальные права API и
  публикация должны быть проверены после подключения владельцем Meta. Ни одного
  реального поста эта ветка сама по себе не публикует.
